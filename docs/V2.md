# Second iteration — maintainability, standardization, and reach

The first iteration asked "can this render a photograph properly?" and the answer is yes. This one asks a
different question: **can someone else maintain it, and can someone else use it?** New features are paused.
[`DESIGN.md`](DESIGN.md) stays the specification, [`ARCHITECTURE.md`](ARCHITECTURE.md) the map and
[`ROADMAP.md`](ROADMAP.md) the backlog; this page is the programme that reorders them.

*Written 2026-10-16. Everything numbered below was measured in this repository, not estimated.*

## What the measurements say, including where they contradict the brief

**The build is not the problem.** The brief named "rebuilding every shader every time" as the pain. That is
not what the clock says: touching `shaders/develop/exposure.wgsl` and rebuilding `sidecar-worker` takes
**1.6 s**, and `npm run generate` — which composes every browser shader *and* rebuilds the colour wasm — takes
**3.7 s** warm. `crates/shaders/build.rs` already emits a `rerun-if-changed` per file, so the dependency graph
is honest and cargo is doing the right thing.

What actually costs time is **coupling, not compilation**. Adding one slider touches seven or eight places
across four languages (ARCHITECTURE's own "Adding a develop control" checklist), and three of those steps fail
*silently* when forgotten:

- a new `shaders/client/*.wgsl` that is not added by hand to `WEB_ENTRIES` is simply never generated — the
  Vite build then fails on an unresolved import, and naga never validates the shader either;
- a wasm request struct without `#[serde(rename_all = "camelCase")]` reads every field as absent, so the
  feature does nothing, everywhere, with no error;
- `npm run check` passes against a stale wasm and stale composed WGSL, so the editor runs old code against
  new TypeScript.

Those are the maintainability target. A trap that a test cannot catch is a trap that will be sprung by
whoever arrives next, and this codebase is explicitly written for whoever arrives next.

**The Immich tie is shallower than it feels.** Grepping for it finds ~120 references, and they sit almost
entirely in one crate:

| Where | References |
|---|---|
| `crates/api` (`immich.rs` is 148 lines; plus `resolve`, `lib`, `export`, `config`, `session`) | ~118 |
| `crates/worker`, `crates/sidecar` | 3 |
| `crates/engine`, `crates/color`, `crates/raw`, `crates/shaders`, `shaders/` — **the whole photo pipeline, ~35,000 lines** | **0** |

Better still, `resolve.rs` already degrades gracefully: its chain is *Immich checksum search → storage
template by date and name → Immich filename search → picker*, and `OpenQuery` already accepts a plain `path`.
Half of the non-Immich path exists; it has simply never been the configuration anyone runs.

**The formatter's one-time cost, at four widths.** The sources are hand-wrapped past what rustfmt will
reproduce, so the diff never reaches zero and the only question is how big a reflow to accept:

| `max_width` | diff lines |
|---|---|
| 100 (rustfmt's default) | 20,365 |
| 140 | 12,583 |
| 160 | 9,688 (559 hunks) |
| 200 | 7,012 |

Against ~41,000 lines of Rust. Even the gentlest setting rewrites about a sixth of the codebase, and it is
entirely mechanical.

## Workstream A — formatting and standardization

The point of a formatter is not beauty, it is that **nobody argues about it and no diff contains noise**. It
is also the cheapest of these workstreams and the one that makes the others readable.

1. **Adopt rustfmt**, in exactly one commit that changes nothing but formatting, with the body recording the
   chosen `max_width`. Add the commit's SHA to `.git-blame-ignore-revs` so `git blame` steps over it
   (`git config blame.ignoreRevsFile .git-blame-ignore-revs`, and GitHub honours the file automatically) —
   this is the step that stops a format migration costing you history.
2. **Gate it in CI** next to clippy, which already denies warnings.
3. **Turn the three silent traps into loud ones**, which is the standardization that matters:
   - derive `WEB_ENTRIES` from the directory rather than a hand-kept list, or fail the build when
     `shaders/client/` holds a file the list does not;
   - make the wasm request structs' camelCase a property a test asserts across all of them, rather than a
     convention each one re-states;
   - have `npm run check` depend on `generate`, so it cannot pass against stale artefacts.
4. **Generate the uniform mirrors instead of hand-writing them.** Fifteen `#[repr(C)]` structs are mirrored by
   hand in WGSL and checked by naga. The check is good and should stay; the *hand-mirroring* is the part worth
   deleting, by emitting the WGSL struct from the Rust definition. This is the largest single item in the
   workstream and the one that most reduces the cost of a new control.

## Workstream B — modularity: a library is a folder, not an Immich

The goal is that Immich becomes **one adapter among several**, not the substrate.

**Reading the code first changed the shape of this.** "Decouple Immich" sounds like one seam; it is three,
and they want separating rather than being merged behind a single trait:

| Concern | Where | What a non-Immich answer looks like |
|---|---|---|
| **Library lookup** — find an original by checksum, name, date-and-name; map paths | `resolve.rs`, `config.rs` | A folder tree plus the storage template `sidecar-template` already renders |
| **Identity and auth** — who is this, and may they see it | `session.rs`, via Immich's `/users/me` and an API key | Single-user, or local accounts. Today `auth_required` *is* `immich.enabled()`, so a folder deployment has no auth story at all |
| **Export destination** — where a finished render goes | `export.rs`: upload, then stack with the RAW | Write beside the original, or to an output folder. `Destination::Device` already exists, so this seam is half-built |

Two of the three are already half-separated, which is why this is cheaper than it looks. The order:

1. **Lookup.** The abstraction over what `resolve.rs` actually needs, implemented twice — the Immich one
   (today's behaviour, moved wholesale) and a folder one. A seam with one implementation is a guess; with two
   it is a design. **Started:** `sidecar_template::find_by_name` fills the one step in the chain that had no
   answer but Immich's, since `resolve.rs` already falls back to the template and the picker but the picker's
   own search returns nothing without Immich.
2. **Replace `immich.enabled()` with the presence of an adapter.** It is `!self.base.is_empty()` today — a
   stringly-typed flag checked in a dozen places. Making "is there an Immich" a type rather than a string test
   is the standardization half of the same change, and it is what stops the next feature re-introducing the
   coupling by accident.
3. **Configuration.** `Root` stops requiring `immich_prefix`; a config can declare a folder library with no
   Immich section at all.
4. **Identity and export destination**, in that order, once lookup proves the pattern.

Keep the Immich adapter first-class throughout. It is the owner's own setup and the reason the project
exists; this is about widening the base, not dropping a user.

This is the unlock for everything in Workstream C, and it is cheap precisely because the pipeline crates never
learned about Immich in the first place.

## Workstream C — reach: where else can this run?

The one rule — every develop module written once in WGSL, running in the browser and on the server — is what
makes this plausible at all. Two targets, very different costs.

**Linux (and macOS/Windows) desktop: closer than anything else, but not as close as this section first
claimed.** It is already a Rust binary that serves a web app and talks to a local GPU through wgpu/Vulkan,
and with Workstream B done the shape is: point it at a folder, start the api and worker on a loopback port,
show the UI. A survey on 2026-10-17 ([`research/desktop-port-survey.md`](research/desktop-port-survey.md))
found four things that change the plan, and the first two invalidate what this paragraph originally said —
that wrapping it in a window was optional and that Tauri would do.

**1. The webview shell cannot be assumed, because WebGPU in a webview does not work on Linux.** Tauri closed
WebGPU support as "not planned"; its flag mechanism works only on Windows WebView2, and its own maintainers
state the Linux and macOS webviews have no way to set such flags. WebKitGTK/WPE 2.52.0 (March 2026) does not
mention WebGPU, and Igalia disabled the GPU process by default for GTK and WPE in February 2026 as not ready.
Even plain Chrome on Linux still documents WebGPU behind two flags. **Every path that reliably has GPU access
on Linux in 2026 is native wgpu, not webview WebGPU** — which should go in DESIGN.md, because it means the
client WGSL stages must keep working through plain wgpu natively, not only through browser WebGPU. The
options, ranked: a **hybrid** — a thin shell for platform integration with the image canvas on a native wgpu
surface — keeps Vulkan and reuses the same WGSL, at the cost of a split rendering architecture; **Electron**
(MIT) ships its own Chromium so the *app* sets the flags rather than the user, which most directly solves the
problem but costs ~150 MB per platform and puts a Node runtime inside the trust boundary, **and is unverified
on Linux WebGPU — test it, don't read about it**; **local server plus the user's browser** (today's shape)
keeps working but asks Linux users to set flags and gives up all platform integration.

**2. A browser-only build cannot be colour-accurate, independent of the WebGPU question.** A browser applies
its own colour management and will not tell the page the monitor profile, so on a wide-gamut or HDR display a
browser-only Sidecar is inaccurate by construction. A native shell is also the only way to get file
associations, "Open with", drag-and-drop from a file manager, native file pickers (and on Flatpak the XDG
portal, which is how a sandboxed app legitimately gains folder access). **That is an argument for a native
shell that has nothing to do with Tauri's WebGPU stance.**

**3. Colour management is now mostly a matter of asking the compositor, on Linux.** `color-management-v1`
shipped in wayland-protocols 1.41 (February 2025) and is at staging version 3. The right design is to **not
read the monitor profile at all**: fetch the output's or surface's image description, render to it, and set a
per-surface rendering intent — perceptual is mandatory, and the optional set includes relative-with-black-
point-compensation and absolute-without-adaptation, which the protocol itself annotates as useful for
proofing. Multi-monitor then falls out structurally, since the preferred description is per surface with
change events. Deliberate limits: no display measurement, and a client cannot set an output's profile.
**Windows is the awkward one** — `AdvancedColorInfo` is UWP-only so desktop apps cannot use it, and Microsoft
says apps should move away from interacting with display ICC profiles directly because their behaviour
changes incompatibly when Advanced Color is on, which invalidates the textbook "lcms2 against the display
profile" design there. **macOS ColorSync and EDR were not researched and are a real gap** in the
"macOS plausible" part of this plan. Libraries are comfortable: lcms2 (MIT), OpenColorIO (BSD-3), moxcms
(Apache-2.0 OR BSD-3, pure Rust) and qcms (MIT). The right shape is to parse ICC and bake transforms into 3D
LUTs on the CPU when the profile changes, and sample them in WGSL — neither library belongs in the per-frame
path. **Soft proofing must be Sidecar's own shader**, since a printer profile is CMYK or N-colour and is
outside what Wayland will accept as an image description; compose working → proof → display into *one* LUT
and compute the gamut warning from the same chain, because a parallel path is exactly how Lightroom's
GPU-only gamut-warning bug happens. darktable's soft proof has no rendering-intent option at all — a cheap
differentiator.

**4. The catalogue is the largest single risk, because Immich *was* the asset manager.** Decoupled, Sidecar
risks becoming a developer without a library — which is precisely darktable's standing criticism, where every
recurring complaint is about file management rather than processing depth. The lowest-risk model is the one
darktable uses and that Sidecar's XMP design already matches: **the database is a rebuildable cache, the
sidecar is the truth.** Table stakes for a first release: add a folder as a watched collection with recursive
scan; a preview cache keyed by content hash and mtime; star rating, pick/reject flag, colour label; keywords;
filter and sort; everything written to XMP. A **catalogue-free "just browse a folder" path is a real
expectation, not a niche one.** darktable's reported failures are a direct warning list: importing a folder
that already had sidecars overwrote them with blank files, and its startup XMP check prompts on sidecars
seconds newer than the database — so never write an XMP during a scan, compare content rather than only
mtime, and offer one explicit conflict resolution rather than a per-file modal. Identify images by stable
content identity rather than path, and re-link on rescan.

**Culling is where the desktop port is an advantage rather than a cost.** The decisive mechanism is reading
the camera's embedded JPEG instead of rendering the raw — one blog's test of 1,000 raws reports 27:35 against
3:07, indicative rather than measured. A browser-plus-server editor is structurally disadvantaged because
every preview crosses an HTTP boundary; a desktop build can memory-map the raw and hand the embedded JPEG
straight to the GPU. The known cost is that a JPEG cannot show clipping — which makes **a raw-derived
clipping warning computed from the raw histogram, needing no demosaic, the differentiating feature**, and it
is squarely inside what the WGSL pipeline already does. Focus peaking and the AF-point overlay are already
culling tools in a form Lightroom lacks; what is missing is the surrounding workflow of ratings, labels,
compare views and collections.

**Packaging, signing and the threat model.** Linux is effectively free (Flathub plus an AppImage; design for
the sandbox's portal-based folder access and Vulkan runtime extensions rather than discovering them late).
macOS and Windows both have a money-and-identity gate: Apple's programme is about $99/year and an unnotarised
app is blocked by Gatekeeper, while Windows signing is structurally hardest — Azure's service is cheap but
eligibility reportedly requires an organisation with a verifiable multi-year history in a limited set of
countries, and sources disagree on the list. A project without an eligible legal entity cannot use it, and
unsigned Windows binaries mean SmartScreen warnings on every download. With Immich gone there is no user
database and no sessions: for a single-user desktop app the answer is **no authentication plus strict
isolation** — bind only to `127.0.0.1`, take an OS-chosen ephemeral port, require a per-launch random token
on every endpoint, reject foreign `Origin`, validate `Host` against an allowlist, and never use cookies for
auth. A unix-domain socket would remove the whole browser-origin attack class but is not reachable from a
browser — another point for a native shell. Path traversal matters much more once the server reads arbitrary
user folders instead of Immich-supplied paths: canonicalise every client path against the configured roots.

**Explicitly out of scope, and worth saying so.** *Tethering*: libgphoto2 is the only realistic cross-platform
library and is LGPL, excluded even dynamically; the compliant routes are invoking a user-installed `gphoto2`
binary or implementing PTP-over-USB on a pure-Rust USB stack — and note `rusb` wraps libusb, itself LGPL, so
that stack is a prerequisite. *Display profiling*: ArgyllCMS is **AGPL-3.0, not GPL**, and because it ships as
command-line tools the "we only shell out" pattern used for HEIC is exactly what AGPL is drafted to cover.
Consume profiles, never measure: the user calibrates with their own tools and Sidecar reads the result, which
is data rather than code. *Printing*: genuinely unresearched rather than deprioritised, and the judgement — a
judgement, not a finding — is that the high-value subset is soft proofing plus a correct 16-bit TIFF with an
embedded output profile, letting the photographer print through whatever they already use. RawTherapee
declines this axis entirely.

**iPhone: partly already true, and the rest is harder than it looks.** The editor is a PWA and Safari now has
WebGPU on Metal, which is the configuration DESIGN already assumes — so *a phone pointed at a Sidecar server*
works today. A **standalone** on-device app is a different proposition, and the blockers are not the renderer:

- `wgpu` → Metal and LibRaw (C++) both build for `aarch64-apple-ios`; `burn` runs on wgpu, so even the ML
  masks are not automatically out.
- **ExifTool is Perl**, and it is shelled out to for export metadata, AF points and HEIC auxiliary images.
  There is no Perl on iOS. Each use needs a native replacement or must be dropped on that platform.
- **The HEIC decoder is an external program** by deliberate licence design (libheif is LGPL-3.0 — see
  CLAUDE.md), and iOS will not run one. On iOS the system decoder is right there and is not LGPL, so this is
  an adapter, but it is a real one.
- **There is no filesystem library on iOS**; there is PhotoKit. That is a third `Library` implementation, and
  it is the strongest argument for doing Workstream B first.
- The full-resolution session buffer assumes server VRAM, which a phone does not have in the same quantities.

So the sequence is: *decouple the library → desktop → re-examine the phone*, and the phone question should be
re-asked once a `FolderLibrary` exists, because by then the answer will be concrete rather than speculative.

## Order of work

1. **A1–A2, rustfmt and its CI gate — done**, at `max_width = 100`. The width was chosen for merges rather
   than for looks: git is line-granular, so two branches touching different arguments of one wide call
   collide in the same hunk, where at 100 those arguments merge cleanly. With a stack of branches that each
   merge `main` back down, that is the difference between a conflict and no conflict, and the last stack cost
   a day to exactly that. The reflow is one commit, recorded in `.git-blame-ignore-revs`.
2. **B1–B3, the `Library` seam.** The keystone: it is what "broader use cases" actually means in code.
3. **C, the desktop target.** It no longer simply falls out of B: the shell and the catalogue are each
   substantial, and the shell question gates whether Sidecar can be colour-accurate at all. Settle the shell
   experiment first (below), then catalogue, then colour management.
4. **A3–A4, the traps and the generated uniforms.** Valuable, but they pay off per *new feature*, and
   features are paused — so they come after the things that widen use.
5. Features resume from ROADMAP afterwards, against a codebase that is cheaper to change.

## Measurements to run, not conclusions to assume

The 2026-10-17 survey ends in questions that no amount of further reading settles. Each gates a decision, and
each is cheap next to the work it would misdirect. In rough priority:

| Question | What it decides | How to settle it |
|---|---|---|
| Does Electron actually give WebGPU on Linux? | The whole shell architecture | An experiment, not a search: `enable-unsafe-webgpu` plus `--use-vulkan`, on AMD/Mesa and on NVIDIA. The project's own rule about verifying in a real browser applies directly |
| Does wgpu expose Wayland `color-management-v1` surfaces or HDR swapchain formats? | Whether colour-accurate and HDR display are reachable at all natively. **The single most load-bearing unknown**; no source found either way | Read the wgpu repository and issue tracker |
| What 3D LUT grid size holds parity? | Colour-transform accuracy. The usual 33³/64³ figures are forum lore | Measure against the existing ΔE2000 parity harness |
| Raw denoiser runtime at full resolution on a consumer or integrated GPU | Whether denoise can ever be live or is export-only | Local benchmark, tiled with overlap. No published figure exists |
| Real-ESRGAN weights, and DIV2K/Flickr2K/OST terms | Blocks or unblocks upscaling | Fetch the dataset terms; ask the author for an explicit grant |
| Places2 and ADE20K dataset terms | Blocks or unblocks any inpainting or segmentation model | Direct check — the host refused connections during the survey |
| In-clone LICENSE reads | Several licences rest on package metadata or a repo sidebar rather than LICENSE text | Read upstream LICENSE for lcms2, moxcms, libavif, dav1d, libjxl, libultrahdr, rav1e; confirm `ort`, `nusb`, the XMP crates, and the ACES RGC CTL terms |
| Current HEVC pool terms for software decoders | Whether the HEIC position is cleared or merely argued. The carve-out usually cited is a 2016 statement absent from the pool's current description | A legal reading, not a web search. Same for the PatchMatch and Upright patent families |

## What this plan deliberately does not do

- It does not re-architect the renderer. The single-source WGSL rule works and is the reason a second platform
  is even arguable.
- It does not drop Immich.
- It does not promise an on-device iPhone app. It promises to find out honestly what one would cost, once the
  library seam makes the question answerable.
- It does not touch the licensing position, which is non-negotiable and already shapes the HEIC and ExifTool
  boundaries above.

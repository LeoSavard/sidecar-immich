# Five blockers reshape Sidecar's desktop roadmap

> *Survey conducted 2026-10-17, across six established desktop RAW editors, the image-processing literature,
> desktop-application requirements, colour management and output, and the licensing of ML models and their
> weights. It is a snapshot with sources, not a specification: ROADMAP.md and V2.md carry the decisions it
> led to, and where the two disagree the roadmap wins. Claims here are cited; the ones that could not be
> sourced say so, and the open questions are collected in V2.md's measurement table rather than guessed at.*

The research turns up one gap that no amount of shader work closes — **Sidecar has no heal, clone or spot-removal tool, and all six established desktop RAW editors do** ([darktable module list](https://docs.darktable.org/usermanual/stable/en/module-reference/processing-modules/); [RawPedia Local Adjustments](https://rawpedia.pixls.us/local_adjustments/); [ON1 features](https://www.on1.com/products/photo-raw/features/?t=2); [PetaPixel on LrC 13.3](https://petapixel.com/2024/05/21/huge-adobe-lightroom-update-adds-ai-generative-remove-and-lens-blurring/)) — and four findings that invalidate routes currently assumed open. The webview route to a desktop shell does not deliver WebGPU on Linux: Tauri closed WebGPU support as "not planned", the flag mechanism it does offer works only on Windows WebView2, and WebKitGTK had its GPU process *disabled by default* in February 2026 ([tauri#12846](https://github.com/tauri-apps/tauri/issues/12846); [tauri#6381](https://github.com/tauri-apps/tauri/issues/6381); [WebKit bug 307065](https://bugs.webkit.org/show_bug.cgi?id=307065)). `docs/ROADMAP.md:354` states that Real-ESRGAN is "BSD-3-Clause for both code and pretrained weights"; the code licence is verified BSD-3-Clause, but the model-zoo page **states no licence for the weights at all**, which grants nothing ([Real-ESRGAN LICENSE](https://raw.githubusercontent.com/xinntao/Real-ESRGAN/master/LICENSE); [model_zoo.md](https://raw.githubusercontent.com/xinntao/Real-ESRGAN/master/docs/model_zoo.md)). ArgyllCMS, the obvious display-profiling dependency, is **AGPL-3.0, not GPL** — harder to work around, and its command-line-tool shape is exactly what AGPL is written to cover ([argyllcms.com/doc/License.txt](https://www.argyllcms.com/doc/License.txt)). SegFormer, the default sky-segmentation answer, ships Apache-2.0 code with weights restricted to "research or evaluation purposes only" ([NVlabs/SegFormer LICENSE](https://raw.githubusercontent.com/NVlabs/SegFormer/master/LICENSE)). Against that, the cheapest high-leverage item in the whole survey is the **guided filter**, which is four box filters plus per-pixel algebra and simultaneously unlocks clarity, dehaze transmission refinement, mask feathering and better depth upsampling ([He, Sun, Tang, TPAMI](https://people.csail.mit.edu/kaiming/publications/pami12guidedfilter.pdf)).

## Five findings to settle before writing roadmap entries

**1. The webview shell cannot be assumed.** Windows WebView2 can enable WebGPU via `additionalBrowserArgs` with `--enable-unsafe-webgpu`; Tauri's own thread states plainly that "the Linux and macOS webviews have no setting to enable flags like these" ([tauri#6381](https://github.com/tauri-apps/tauri/issues/6381)). WebKitGTK/WPE 2.52.0 (March 2026) does not mention WebGPU, and Adrián Pérez disabled the GPU process by default for GTK and WPE in February 2026, keeping it compiled but "not yet ready for prime time" ([Igalia WIP #60](https://blogs.igalia.com/webkit/blog/2026/wip-60/); [bug 307065](https://bugs.webkit.org/show_bug.cgi?id=307065)). Chrome on Linux still documents WebGPU behind *two* flags — `#enable-unsafe-webgpu` and `#enable-vulkan` — and gives no Linux version number at all ([Chrome WebGPU troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)). Secondary reports on Linux default-on hardware conflict: one says Intel Gen12+ gets WebGPU by default in Chrome 144 stable, another describes the same support as Chrome 144 *Beta*, and an NVIDIA-in-147-Wayland-only claim could not be corroborated ([webgpu.com](https://webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/); [LuciadRIA setup](https://dev.luciad.com/portal/productDocumentation/LuciadRIA/docs/articles/tutorial/getting_started/setup_webgpu.html)). The practical consequence is architectural and should be written into DESIGN.md: **every path that reliably has GPU access on Linux in 2026 is native wgpu, not webview WebGPU**, so the WGSL client stages must keep working through plain wgpu on the native side. Electron ships its own Chromium and can set the flags itself, which is the option that most directly solves this — but **Electron's WebGPU-on-Linux behaviour is unverified in the research and must be measured, not searched**.

**2. The upscaling roadmap entry is wrong on the load-bearing clause.** Real-ESRGAN's surrounding stack is genuinely clean and verified by direct LICENSE fetch: code BSD-3-Clause, `Real-ESRGAN-ncnn-vulkan` MIT, ncnn BSD-3-Clause with permissive third-party components ([ncnn LICENSE](https://raw.githubusercontent.com/Tencent/ncnn/master/LICENSE.txt)). The weights are the hole, and the checkpoints are named after their training sets (`ESRGAN_SRx4_DF2KOST_official` = DIV2K + Flickr2K + OST), whose NTIRE-tradition terms are typically research-use and **could not be verified in this research**. Safest reading: a weights file with no licence statement grants nothing. The fix is one of three — an explicit grant from the author, a checkpoint whose card states a permissive licence, or retraining on BasicSR (verified Apache-2.0, [LICENSE.txt](https://raw.githubusercontent.com/XPixelGroup/BasicSR/master/LICENSE.txt)) over imagery Sidecar may use. Also correct the collateral: chaiNNer/Upscayl were already flagged as excludes, and Upscayl's AGPL-3.0 is verified ([LICENSE](https://raw.githubusercontent.com/upscayl/upscayl/main/LICENSE)).

**3. ArgyllCMS is AGPL-3.0, which closes the shell-out escape too.** Verified two ways: `License.txt` returns the full AGPLv3 text and nothing else, and the home page describes the tools as "licensed under an AGPL license" with a separate commercial-licensing page; current version 3.5.0, 4 February 2026 ([argyllcms.com](https://www.argyllcms.com/)). Because Argyll ships as command-line tools, the HEIC-style "we only invoke an external binary" pattern is the precise case AGPL is drafted to make ambiguous. The clean boundary is **data, not code**: the user calibrates with DisplayCAL/Argyll or vendor software themselves, the OS holds the resulting profile, and Sidecar reads the profile. Argyll's file formats (`.ti1`/`.ti3`, `.cal`) and documented methods stay usable. Building profiling into Sidecar would mean instrument drivers — recommend explicitly out of scope.

**4. Sky segmentation should not go through SegFormer, and probably should not go through a network at all.** SegFormer's LICENSE is the "NVIDIA Source Code License for SegFormer", permitting use only "non-commercially … for research or evaluation purposes only" while reserving NVIDIA's own commercial use. mmsegmentation is Apache-2.0 but its zoo checkpoints inherit each method's own licence, so the trap re-enters there ([mmsegmentation LICENSE](https://raw.githubusercontent.com/open-mmlab/mmsegmentation/main/LICENSE)). SAM 2 code is Apache-2.0 ([LICENSE](https://raw.githubusercontent.com/facebookresearch/segment-anything-2/main/LICENSE)); SAM 3 is reported to use a custom "SAM License" and should be treated as unusable until its text is read ([arXiv 2605.23500](https://arxiv.org/pdf/2605.23500)). Ultralytics tooling is AGPL-3.0 and is not a usable source of code or weights ([Ultralytics ADE20K](https://docs.ultralytics.com/datasets/semantic/ade20k)). The better route exploits infrastructure Sidecar already has: **sky is the far plane of the existing Depth Anything V2 map**, combined with a low-texture/chromaticity prior, the existing BiRefNet subject mask as a negative constraint, and a guided filter to finish the edge. Zero licence risk, no new model download. ADE20K's and Places2's own dataset terms could not be retrieved (`places2.csail.mit.edu` refused the connection) and are a required follow-up before shipping anything trained on them.

**5. Retouching is the one gap with no substitute and real architectural weight.** It is present in all six competitors and is the first thing a user reaches for on a dust spot. It is not another WGSL stage with a scalar parameter set: it needs **per-patch records in the XMP history** rather than sliders. The notes' recommendation is to build exactly one non-destructive parametric heal/clone — source-offset patch, feathered edge, wavelet- or Poisson-blended — and stop. Generative inpainting is a trap for an Apache-2.0 self-hosted project: Lightroom's Generative Remove runs server-side on Firefly, requires an internet connection, is a premium feature, and shipped in early access described contemporaneously as "*very* beta" ([Adobe help](https://helpx.adobe.com/lightroom/mobile/heal-clone-and-remove/remove-objects-with-generative-remove.html); [PetaPixel](https://petapixel.com/2024/05/21/huge-adobe-lightroom-update-adds-ai-generative-remove-and-lens-blurring/)). If a learned inpainter is wanted later, LaMa's repository LICENSE is verified Apache-2.0 but **the weights' licence is asserted only by Hugging Face mirrors, with no upstream statement**, and it was trained on Places2 whose terms nobody quotes ([advimman/lama LICENSE](https://raw.githubusercontent.com/advimman/lama/main/LICENSE)). PatchMatch carries unresolved Adobe patent exposure — prefer Criminisi-style exemplar fill or an exhaustive GPU nearest-neighbour search ([PatchMatch paper](https://pixl.cs.princeton.edu/gfx/pubs/Barnes_2009_PAR/patchmatch.pdf); [US8818135B1](https://patents.google.com/patent/US8818135)).

## (a) Image-processing areas of interest

The pattern worth exploiting: a small number of primitives unlock many features. One good Gaussian/Laplacian pyramid kernel plus coefficient remapping buys clarity, texture, local contrast, shadow/highlight recovery and tone mapping at once; one guided filter buys dehaze refinement, mask feathering and better depth upsampling. Build the primitives, not the features.

### Tier 1 — cheap, high leverage, reuses what exists

| Item | What it is and why it matters | What it takes | Licence position |
|---|---|---|---|
| **Guided filter** | Edge-preserving filter on a local linear model, with "better behaviors near edges" than the bilateral and a "fast and nonapproximate linear time algorithm, regardless of the kernel size" ([TPAMI](https://people.csail.mit.edu/kaiming/publications/pami12guidedfilter.pdf)). It is the workhorse under clarity, dehaze transmission refinement, mask feathering and depth upsampling. | Four box filters (mean of I, p, I·p, I²) plus per-pixel algebra — ideally suited to WGSL. Subsampled "fast guided filter" reports ">10× speedup with almost no visible degradation" ([arXiv 1505.00996](https://ar5iv.arxiv.org/html/1505.00996)). It is also the cheaper, more standard replacement for Sidecar's existing joint-bilateral depth upsampling, which ROADMAP already notes is a single pass that leaves edge error behind. | Papers; implement from scratch. |
| **ACES Reference Gamut Compression** | "A simple RGB ratio based algorithm which compresses values based on their distance from the neutral axis", introduced in ACES 1.3 as a "technical correction rather than an aesthetic look", replacing the deprecated Blue Light Artifact LMT; ACES 2.0's display gamut compression **uses the same curve** ([RGC overview](https://docs.acescentral.com/rgc/overview/); [ACES 2.0 gamut compression](https://draftdocs.acescentral.com/output-transforms/technical-details/gamut-compression)). Fixes the blue/magenta breakdown from saturated LED and neon that white balance and an HSL mixer cannot. | Closed-form, seven scalar parameters (limit, threshold and roll-off per cyan/magenta/yellow as exposed by OCIO 2.1), no LUTs, no iteration, invertible — on the order of 30 lines of WGSL ([OCIO 2.1 notes](https://opencolorio.readthedocs.io/en/main/releases/ocio_2_1.html)). | Spec is public; OCIO is BSD-3-Clause; aces-core Apache-2.0 per project rules. **Two caveats:** no licence statement was found for the RGC CTL code in `aces-dev`/`aces-core`, and the transform ID differs between ACES documents (`LMT.Academy.GamutCompress.a1.3.0` vs `LMT.Academy.ReferenceGamutCompress.a1.v1.0`) — resolve against the targeted release. |
| **Hue-preserving tone mapping** | "Applying a non-linear curve to RGB channels distorts colors" ([pixls.us](https://discuss.pixls.us/t/new-feature-automated-gamut-mapping/11783/)); the fix is to apply the curve to a luminance/norm and handle chroma separately. Sidecar's base curve is already a logistic, so this is a small change with a large look consequence. | Reshape the existing curve stage. Practitioner comparison notes AgX and sigmoid both "tend to need extra saturation control" and that raising hue preservation "made colors look more realistic" ([pixls.us](https://discuss.pixls.us/t/module-proposal-gamut-compression/52532?page=3)). A 2025 Electronic Imaging paper gives a lower-cost RGB/YUV hue-preserving method that avoids the perceptual-space round trip ([IPAS-226](https://library.imaging.org/ei/articles/37/10/IPAS-226)). | Papers. |
| **Variance-stabilising transform around existing wavelet NR** | Raw noise is Poisson-Gaussian per CFA plane; the existing wavelet NR implicitly assumes uniform-variance Gaussian, which is why wavelet NR is habitually too strong in shadows and too weak in highlights. Foi's pipeline stabilises variance, denoises with a Gaussian-assumption filter, then applies an **exact unbiased inverse**, where "the choice of the proper inverse transformation is crucial in order to minimize the bias error" ([Foi, optimal inversion](https://webpages.tuni.fi/foi/invansc/)). | Two per-pixel scalar functions (inverse usually a small LUT) wrapped around a stage that already exists. RPG-VST applies the generalised Anscombe transform **per CFA plane with separate shot and read parameters per channel** and argues OLS calibration is brittle on "contaminated low-texture statistics" ([arXiv 2607.24291](https://arxiv.org/pdf/2607.24291)). Azzari & Foi warn the Anscombe transform "can be quite inaccurate" below one count per pixel ([paper](https://webpages.tuni.fi/foi/papers/Azzari_Foi-Iterative_Poisson_denoising-2016_plus_supplementary.pdf)). vkdt's noise-profile fitting has had real failure cases from integer overflow — guard rails required ([pixls.us](https://discuss.pixls.us/t/released-vkdt-0-5-0/34420?page=3)). | Papers. vkdt is BSD-2-Clause (check per file). |
| **Highlight-aware demosaic** | Standard interpolators mix clipped and unclipped neighbours, generating magenta/green fringes at highlight edges *before* highlight reconstruction ever runs. A real gap, not discussed much in the literature. | A per-channel clip-mask texture and a renormalised weight sum inside the existing RCD WGSL kernel. Cheap addition, no new algorithm. | Own work. |
| **Upright estimator** | Lee, Shechtman, Wang & Lee, CVPR 2012 / TPAMI 2014: detect lines, estimate vanishing points and camera calibration robustly, optimise a homography against criteria derived from **human perception studies** ([Adobe Research](https://research.adobe.com/publication/automatic-upright-adjustment-of-photographs-with-robust-camera-calibration); [POSTECH PDF](https://cg.postech.ac.kr/papers/06_Automatic-Upright-Adjustment-of-Photographs-with-Robust-Camera-Calibration.pdf)). Sidecar already has the warp — crop, straighten, keystone — so only the estimator is missing. High visibility for low cost. | Line detection on GPU; vanishing-point RANSAC/J-linkage and homography optimisation are small CPU problems over a few hundred segments. **Ordering constraint:** detect lines on the *distortion-corrected* image, since lens correction already runs — otherwise straight architectural lines are curved and the vote is biased ([ULPGC](https://accedacris.ulpgc.es/bitstream/10553/35433/2/automatic-correction-perspective.pdf)). | Papers free to implement. **This is the one area with active Adobe-adjacent patent filings** — US10354364B2, US9519954, US8045804 — a freedom-to-operate question worth a look before shipping, not a licensing one. The TPAMI equations are needed; the specific perception-study energy terms were not verified in this research. |

### Tier 2 — substantial but well-bounded

| Item | What it is and why it matters | What it takes | Licence position |
|---|---|---|---|
| **Local Laplacian filters for clarity/texture** | Paris, Hasinoff, Kautz, SIGGRAPH 2011: point-wise remapping of Laplacian pyramid coefficients gives edge-aware filtering "without degrading edges or introducing halos, even at extreme settings" ([project page](https://people.csail.mit.edu/sparis/publi/2011/siggraph); [CACM version](https://people.csail.mit.edu/sparis/publi/2015/cacm/Paris_15_Local_Laplacian_Filters.pdf), the more readable write-up for implementers). Sidecar's gap is specifically **halo-free local contrast at large radius**, not another global curve. | The fast-LLF discretisation — a fixed set of remapping levels, interpolated between resulting pyramids — is the right GPU shape: a fixed number of full pyramid passes, no divergence, no atomics ([fast LLF](https://imagine.enpc.fr/~aubrym/projects/llf/index.html)). Same kernels then serve exposure fusion and tone mapping. | Papers. darktable's `diffuse or sharpen` is documentation only; its code is GPL-3.0 and off limits. |
| **Single-image exposure fusion** | Mertens, Kautz, Van Reeth: skip HDR assembly entirely, weight each pixel by **contrast, saturation and well-exposedness**, blend the stack through a Laplacian pyramid ([paper PDF](https://www.cs.princeton.edu/courses/archive/spring14/cos426/papers/Mertens07.pdf)). Applied to synthetic exposures from one RAW it is a strong, cheap shadow/highlight recovery stage sharing the pyramid kernels above. | Reuses the Laplacian pyramid. The IPOL walkthrough (Hessel, 2018) is the companion document and documents the **saturation artefacts** — the saturation weight misbehaves on near-neutral and clipped pixels ([IPOL PDF](https://www.ipol.im/pub/art/2018/230/article.pdf)). | Papers; IPOL article text safe regardless of its code licence. |
| **Blind dehaze (Dark Channel Prior)** | Pipeline is atmospheric light → transmission estimate → **transmission refinement** → reconstruction ([EURASIP review](https://jivp-eurasipjournals.springeropen.com/track/pdf/10.1186/s13640-016-0104-y)). Documented failure modes are "halo artefacts, sky misestimation, and reduced accuracy in complex scenes" ([review](https://app.mypolycc.edu.my/journal/PMJET/article/view/899)), both mitigated by guided-filter refinement — and the guided filter was invented partly to replace DCP's slow soft matting, by the same authors. Note Sidecar **already has haze-by-distance from its depth map**, which is the better-conditioned problem: with a depth map, transmission t = exp(−β·d) is direct and the fragile estimation step is skipped. The genuine gap is *blind* dehaze where depth is unavailable, plus DCP transmission as a cross-check on depth. | Min-filter over a window, a percentile reduction for atmospheric light (histogram with atomics, or approximated on a downsampled mip), guided-filter refinement, per-pixel reconstruction. The **2024 IPOL article** is peer-reviewed *with* a precise algorithmic description and is the single best implementation target ([IPOL 2024/530](https://ipol.im/pub/art/2024/530)). | Papers. Berman's non-local prior is the principled alternative but needs spherical clustering with atomics and is materially more complex ([CVPR 2016](https://openaccess.thecvf.com/content_cvpr_2016/papers/Berman_Non-Local_Image_Dehazing_CVPR_2016_paper.pdf)). |
| **Lens-aware RL deconvolution** | Richardson-Lucy is "one of the most GPU-friendly algorithms in this whole survey": per iteration, two separable convolutions and two elementwise passes. It "tends to amplify noise", so regularisation is required; the TV term "suppresses unstable oscillations while preserving object edges", and Laasmaa et al. derive the regularisation parameter **automatically from the images as the algorithm progresses** — the detail that makes this a slider rather than an expert control ([PMC3222693](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC3222693/)). Halos come from a wrong PSF or too many iterations, not from RL ([Strolls with my Dog](https://www.strollswithmydog.com/richardson-lucy-algorithm/)). **Differentiated for Sidecar because lens correction already means lens identification**: a per-lens, radially varying PSF turns RL from a global guess into a calibrated correction — and DxO's "Local Lens Sharpness Optimization" is the one thing nobody else has ([Thomas Fitzgerald](https://blog.thomasfitzgeraldphotography.com/blog/2025/9/dxo-releases-photolab-9-with-ai-masking-and-expanded-local-adjustments)). | Tile the image, select a PSF per tile from a small table indexed by radius and aperture, run the same kernel per tile — mirroring the spatially-varying gather radius already implemented for lens blur. Halo avoidance is three cheap things: clamp PSF radii to physically plausible values, bound iterations, and mask deconvolution away from clipped highlights and noise-dominated regions. | Papers. Bilateral-RL is patent-encumbered (US8406564) — use TV regularisation instead. |
| **Non-local means (with VST)** | The much better first step than BM3D: pure gather, fixed work per pixel, no atomics, trivially tileable with the search window in `var<workgroup>`. Combined with VST it is a credible mid-tier denoiser; its low-frequency blotching is covered by the existing wavelet NR's coarse scales. | Straightforward WGSL. | Papers. |

### Tier 3 — the real quality headroom, and a design decision the port should make now

Multi-frame is where the remaining quality lives. Wronski et al. "replaces traditional demosaicing … with a multi-frame merge that creates a complete RGB image directly from a burst of CFA raw images", using natural hand tremor, at **100 ms per 12-megapixel RAW input burst frame on mass-produced mobile phones** — firmly within a desktop GPU's budget ([Google Research](https://research.google/pubs/handheld-multi-frame-super-resolution/); [arXiv PDF](https://arxiv.org/pdf/1905.03277.pdf)). The structure is GPU-native: coarse-to-fine alignment pyramid, per-output-pixel kernel regression with anisotropic kernels from local structure tensors, and a robustness mask falling back to single-frame where frames disagree — all gather-based, accumulation done per output pixel rather than by scatter, so no atomics. An independent **IPOL reimplementation** exists (Lafenetre, Facciolo, Eboli, 2023), peer-reviewed with a complete algorithmic description; the article text is safe to implement from, but **its code licence was not retrieved and IPOL code licences vary by article — check before anyone reads the source** ([IPOL announcement](https://tools.ipol.im/mailman/archive/discuss/2023-July/001560.html)).

**Pixel-shift sensor modes are the easier special case and the better first increment**: Pentax, Sony, Panasonic, Fuji and Olympus bodies know their sub-pixel offsets by design, so only the merge and robustness mask are needed, not the alignment pyramid — a real differentiator, since few editors handle pixel-shift raws natively. Focus stacking is mostly a focus-measure plus pyramid-blend problem, and Sidecar already computes a Laplacian over local standard deviation for focus peaking, which *is* a focus measure. The hard part is alignment, and the literature is explicit that **focal breathing shifts the field of view across slices** so sharpness cannot be compared at the same coordinates, and "existing optical flow frameworks can't be used directly for alignment because defocus blur breaks the brightness constancy assumption" ([arXiv 2207.09658](https://arxiv.org/pdf/2207.09658)) — a similarity transform per slice at minimum.

The architectural point matters more than any single feature: **multi-frame work needs several full-resolution raw frames resident on the GPU at once, and a single-image pipeline's memory model and node graph may not accommodate that.** That is a decision better made during the desktop port than retrofitted. Alignment-and-merge is also the shared infrastructure for HDR merge, averaging denoise, astro stacking and ghost removal, so its value exceeds any one feature it unlocks. vkdt already does "aligning multiple raw files and merging them" in GLSL/Vulkan and is BSD-2-Clause per Sidecar's own notes — verify per file, since a few vkdt files are GPL-3.0 ([vkdt README](https://www.github.com/hanatos/vkdt)).

### Where the research found no answer

Demosaic beyond RCD has **no measured benchmark in circulation** — the comparisons are user-manual prose and forum posts, which means any claim that something beats RCD is currently unsupported by published numbers. darktable's manual says AMaZE and RCD "both reconstruct fine detail and edges well, but can produce color overshoots", that AMaZE "is more prone to color overshoots than RCD", and that "LMMSE is better suited for use on high ISO and noisy images" ([darktable demosaic manual](https://docs.darktable.org/usermanual/5.6/en/module-reference/processing-modules/demosaic/)); RawPedia agrees RCD "does an excellent job for round edges" and that for higher ISO "LMMSE or IGV are better" ([RawPedia](https://rawpedia.rawtherapee.com/Demosaicing)). The useful inference is that **the highest-value demosaic work is not a new interpolator but noise-aware switching**: colour overshoot on noisy files is exactly what a fitted noise profile predicts, so blend toward a smoother interpolation or denoise-before-demosaic. LMMSE itself is reimplementable from Zhang & Wu (IEEE TIP 2005). No 2025/2026 paper proposing a classical interpolator superseding RCD was found; no raw-domain (Bayer/linear) denoising benchmark for 2025/2026 was found, only sRGB comparisons; and no controlled perceptual study ranking local Laplacian against guided-filter clarity exists — the choice is made on engineering grounds. On profiling, the honest reading is that **spectral profiling is theoretically better but its inputs are hard to obtain reliably**: a 2015 JOSA A study measured ground truth for two cameras and concluded the estimation techniques tested "were not accurate enough compared with the measured data" ([UEA record](https://ueaeprints.uea.ac.uk/id/eprint/52181/)), and a critique notes that low error on a 24-patch chart does not show the curves are correct since many sensitivity sets predict the same patch values ([dpreview thread](https://www.dpreview.com/forums/threads/interesting-paper-spectral-sensitivity-estimation-without-a-camera.4737183/page-2)). Dual-illuminant DCP is practical and ubiquitous, and Sidecar already interpolates camera matrices by illuminant — so the incremental item is DCP's **forward matrix plus HueSatMap/LookTable**, data plumbing with a small 3D-LUT sampler, not an algorithm.

## (b) Missing photo-editor features relative to the category

Two things to hold onto. First, Sidecar's spectral film simulation is **genuinely unusual** — none of the six competitors does spectral rendering from manufacturer datasheets; the nearest equivalents are LUT packs, darktable's `negadoctor` and ON1's Negative Mode. Sidecar is ahead on the unusual and behind on the boring. Second, Adobe's treatment of Lens Blur sets the completion bar: it was extended to support presets, adaptive-blur presets and **batch editing**, i.e. "works in presets and in batch" is a completion criterion, not an extra ([Julieanne Kost](https://jkost.com/blog/2024/05/lightroom-classic-v13-3-generative-remove-early-access-lens-blur-additional-tether-support-and-more.html)). For Sidecar that means ML masks and depth masks need **deterministic re-derivation per image** to survive batch application — a design constraint, not a UI task.

| **Dehaze** | In all three of Lightroom, darktable and RawTherapee — RawTherapee has *two* paths, a global Haze Removal tool plus a 5.12 Raw Black Points "Dehaze" option that "sets the black points to the minimum values in the image" ([RT 5.12](https://www.rawtherapee.com/downloads/5.12)). | See Tier 2 above; cheap once the guided filter exists. | |
| **Scene-to-display tone transform** | **This is becoming the consensus default, not an option.** darktable made `sigmoid` the default tone mapper for new installs in 5.2.0 and added `AgX` "based on Blender's AgX display transform" in 5.4.0; RawTherapee 5.12 added a sigmoid-based tone mapper ([darktable releases](https://github.com/darktable-org/darktable/releases); [RT 5.12](https://www.rawtherapee.com/downloads/5.12)). An editor shipping with only exposure/contrast/curve will clip highlights in a way that reads as wrong to users arriving from any of these. | Sidecar's logistic base curve is already most of the way there; the missing half is hue-preserving application plus gamut compression. | AgX and ACES RGC are both implementable from Apache-2.0 / published sources. |
| **Camera profile selection** | **A correctness issue, not a feature.** darktable exposes `input color profile`, `unbreak input profile`, `rgb primaries`, `color calibration`; Lightroom has Profiles, Adaptive Profiles (Feb 2025, intensity 0–200) and a legacy Calibration panel ([darktable modules](https://docs.darktable.org/usermanual/stable/en/module-reference/processing-modules/); [Julieanne Kost](https://jkost.com/blog/2025/02/adaptive-profiles-in-lightroom-classic-lightroom-and-camera-raw.html)). If Sidecar does not expose a camera-profile choice, its colours differ from every competitor on the same file and users read it as a bug. | DCP forward matrix + HueSatMap/LookTable, plus ICC input profile loading. | White balance corrects for *both* the illuminant and the camera's uneven spectral response, so temperature alone ignores the second ([pixls.us](https://discuss.pixls.us/t/dual-illuminant-camera-profiles-without-dcp-in-darktable/43887)). |
| **Colour grading wheels** | Table stakes for the "look" half of the workflow, and the OKLCh HSL mixer **does not substitute** — wheels work on tonal ranges, the mixer on hue bands; they are orthogonal. Lightroom has a dedicated Color Grading panel; darktable has `color balance rgb` with lift/gamma/gain and 4-way slope/offset/power/brilliance. | A shadows/midtones/highlights lift-gamma-gain (or slope-offset-power) operator is a handful of lines of WGSL on top of what Sidecar already computes. Best cost/benefit of any pro feature in the survey. | |
| **Gradient masks** | Universal: ON1 lists AI, brush, gradient, luminosity, line, colour-range and depth masks; Capture One describes "linear and radial gradient masks and the brush tool"; darktable has `graduated density` ([ON1](https://www.on1.com/products/photo-raw/features/?t=2); [Capture One](https://www.captureone.com/en/explore-features/whats-new)). | Analytic in the shader — already on Sidecar's roadmap as a third layer kind. | |
| **Presets / styles, copy-paste, sync across a selection** | **Presets are not a feature, they are a distribution channel.** darktable 5.0.0 shipped camera-specific styles for 500+ camera models; Adobe ships Adaptive Sky/Portrait/Subject presets that carry an ML mask rather than fixed sliders. Sidecar's spectral film simulation is exactly the kind of thing that wants a style container — a preset system is a prerequisite for shipping it as a library. And "no built-in presets" is levelled at darktable *despite* its styles system, which tells you presets must be discoverable, shipped with content, and in the default UI. | darktable's model is instructive: history-stack copy/paste/compress across a selection and a styles panel as a first-class lighttable surface, separate from the per-image darkroom history. | **The gap most likely to bite the port is "apply this to the other 200 frames"** — settings-subset copy/paste, sync-across-selection, auto-sync. Unglamorous, and the difference between a developer tool and something usable on a shoot. |
| **Snapshots and virtual copies** | The industry splits versions into two primitives and users expect both: **duplicates/virtual copies** (a second entry sharing one raw, for delivering two looks) and **snapshots** (named states inside one entry, for A/B while editing). Sidecar's XMP already carries history and versions, so this is likely UI. | A snapshot list and side-by-side compare. darktable added centre-view side-by-side snapshots only in 5.2.0 and users liked it immediately. | |

### Tier 2 — expected of a serious editor, cheap for Sidecar specifically

**Soft proofing with a gamut check is the cheapest pro-credibility win available**, because it is almost entirely a rendering-path feature and sits directly adjacent to the Rec.2020/HDR export work already on the roadmap. It needs five pieces: a printer/paper ICC profile (typically CMYK or N-colour, so **not** a three-channel Display-class profile — which confirms the proof transform must be Sidecar's own shader, not delegated to the compositor); a selectable rendering intent for the image→proof step; black point compensation as a toggle; paper-white and ink-black simulation; and a gamut-warning overlay driven by whether the round trip clipped. Two failure modes are documented well enough to design against. First, **compute the warning on the same transform chain as the preview** — Lightroom's gamut warning was reported wrong *only with GPU acceleration enabled*, with the GPU path said to be hard to fix, which is the exact signature of a parallel code path ([Adobe forum](https://community.adobe.com/t5/lightroom-classic/destination-gamut-warning-color-shift/m-p/10138732)). Second, the two-LUT hazard: a simulated-proof preview LUT does not contain the same data as the rendering LUT, so either compose the whole chain (working space → proof with intent/BPC → display) into **one** 3D LUT per configuration, or chain device→PCS transforms through the simulated device, which is correct but slower ([US 6603483](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/6603483)). darktable's soft proof has **no rendering-intent option** because its internal renderer does not support intent ([pixls.us](https://discuss.pixls.us/t/soft-proofing-with-darktable/18277)) — a concrete differentiator available cheaply. Note that almost all the soft-proofing user evidence is 2018–2020 and a targeted search for 2025–2026 complaints returned none; present these as persistent, well-known failure modes rather than current bug reports. Experienced users also push back usefully: soft proofing reveals **tonal loss and out-of-gamut colours, not overall colour-balance shifts**, and it emulates reflective paper on a transmissive monitor, so it can never fully preview a print ([Cambridge in Colour](https://www.cambridgeincolour.com/forums/thread65052.htm)).

Also in this tier: **3D LUT loading** (darktable has `LUT 3D` and `color look up table`); **defringe** as a post-demosaic colour-based tool distinct from raw CA correction; **film-negative inversion** for scans (darktable `negadoctor`, ON1's 2026 Negative Mode); **output framing, watermark and resize** (RawTherapee renamed Resize to "Resize & Framing" in 5.12); and **a culling/rating workflow**, discussed under the port below. Note one trap in reading darktable's deprecation list — `defringe` and `spot removal` being deprecated there does **not** mean the capabilities are unwanted; their specific implementations were superseded by better CA handling and by `retouch`.

### Tier 3 — expected of an "all-in-one", not of a RAW developer

HDR merge, panorama and focus stacking sit awkwardly: ON1 and Lightroom have all three, darktable and RawTherapee have none (users go to Hugin/enfuse). That split suggests they are not table stakes for a RAW *developer* but are expected of anything calling itself all-in-one. Panorama is already on Sidecar's roadmap; HDR merge and focus stacking are its consistent companions, and focus stacking is cheap given existing focus peaking and depth. All three ride on the multi-frame alignment infrastructure above.

### On ML features: what is winnable and what is not

Every commercial generative-fill feature of note in 2026 is a cloud service, which an Apache-2.0 desktop app cannot match and should not try to. **The features that are purely local and purely learned — denoise and upscale — are exactly where Sidecar can compete, and exactly where weights are the bottleneck.** Raw denoise is the one big ML feature where the licensing problem solves itself: MIT noise-synthesis code + Apache-2.0 architecture + Sidecar's own training data = Apache-2.0 weights that belong to the project. Verified-permissive components: NAFNet (MIT + Apache-2.0 text), Restormer (MIT — which contradicts a widespread belief that it is academic-only; the file as of 2026-10-17 is MIT), SwinIR (Apache-2.0), SCUNet (Apache-2.0), BasicSR (Apache-2.0), Sony Research's CVPR 2025 noise modelling (MIT, needs only dark-frame capture, cutting noise-synthesis preparation "from days to hours"), and the ICCV 2021 Noise-Synthesis repo (MIT). Intel Open Image Denoise is Apache-2.0 **including its weights repository** — a useful precedent that shipping Apache-2.0 weights inside an application is normal practice — but it is trained for Monte-Carlo render noise with auxiliary albedo/normal buffers, has **no Vulkan backend**, and neither its runtime nor its weights transfer to Bayer sensor noise ([OIDN overview](https://www.intel.com/content/dam/develop/external/us/en/documents/07-open-image-denoise-807276.pdf); [oidn-weights LICENSE](https://raw.githubusercontent.com/RenderKit/oidn-weights/master/LICENSE.txt)). Note the useful corollary from the denoising literature: DNNs trained on synthetic Gaussian noise performed well on real data ([arXiv 2011.03462](https://arxiv.org/pdf/2011.03462)), which means **a VST front end makes a Gaussian-trained network usable on raw**. A raw denoiser runs on the full mosaic at full resolution, which is why DeepPRIME takes seconds-to-minutes on desktop GPUs; tiled inference with overlap is mandatory on a modest integrated GPU, and the feature should be an explicit, progress-barred export-time operation, not a live pipeline stage. **No published runtime measurement of any open raw denoiser at full resolution on a specific consumer or integrated GPU was found** — any cost figure would be invention.

For auto-white-balance, **implement the paper, not the repo**: Afifi & Brown's Deep White-Balance Editing README states "This software is provided for research purposes only and CAN NOT be used for commercial purposes" and the repo has **no LICENSE file at all**; WB_sRGB's README restricts "the software and the dataset", so retraining on it is blocked too ([Deep_White_Balance README](https://raw.githubusercontent.com/mahmoudnafifi/Deep_White_Balance/master/README.md); [WB_sRGB README](https://raw.githubusercontent.com/mahmoudnafifi/WB_sRGB/master/README.md)). Grey-world, white-patch/max-RGB and grey-edge are textbook and free. Auto-tone is better framed as a parametric fit — percentile anchoring into Sidecar's own tone operator, plus face-aware exposure from the YuNet detections already present — than as a learned regressor; **no permissively licensed learned auto-tone model surfaced at all.**

Runtime choice is not a licensing question: burn (Apache-2.0), candle (dual), tract (dual), ONNX Runtime (MIT) and ncnn (BSD-3) are all verified permissive. It is an engineering question — burn-wgpu keeps one GPU abstraction and no shipped native blob at the cost of slower kernels and ONNX-import coverage gaps; ncnn gives hand-tuned Vulkan kernels with a proven AMD/Intel/NVIDIA record at the cost of a second runtime and model format. **Stay on burn-wgpu and reach for ncnn only if a specific model's throughput is unacceptable.** `ort`'s licence could not be confirmed and must be checked before use. Depth Anything's published timings are expressed in V100/A100/TensorRT terms — a reminder that nearly all published inference benchmarks assume CUDA and say nothing about Vulkan on integrated GPUs.

The policy worth writing down: **weights are a dependency with a licence, tracked in `NOTICE` and `THIRD_PARTY_NOTICES.md` exactly like source**, with three acceptable statuses — explicit permissive licence in the weights' own repo or card, trained in-house, or not shipped. "The code is Apache-2.0" is never sufficient, and a GitHub badge is not a weights licence. Download-on-first-use does not change the licensing position (Sidecar still directs the fetch) but it does change the packaging position, and for anything merely plausible it is the safer shape with the licence shown at fetch time. The **dataset layer is the least examined and most dangerous**: Places2 (LaMa), ADE20K (segmentation), DIV2K/Flickr2K/OST (Real-ESRGAN) and Afifi's WB dataset all sit under terms that are research-only or unverified, and no model card resolves that.

## (c) What the desktop port itself forces

### The shell, and the thing it is actually for

Beyond WebGPU, the decision is about what a shell buys. A browser-based UI can do **none** of: file associations and "Open with", OS drag-and-drop from a file manager, native file pickers (and on Flatpak, the XDG Desktop Portal chooser, which is also how a sandboxed app legitimately gains folder access), or reading the display's colour profile. **The last one is the one that matters for a photo editor**: a browser applies its own colour management and generally will not tell the page the monitor profile, so on a wide-gamut or HDR monitor a browser-only build cannot be colour-accurate by construction. That is a strong argument for a native shell independent of the WebGPU question.

Ranking the options, given Linux-first, WebGPU-required and Apache-2.0: **local server plus the user's own browser** (today's shape) has no licensing concern, the smallest binary and universal coverage, but means asking Linux users to set two Chrome flags, and loses all platform integration. **Electron** (MIT) ships its own Chromium so the app sets the flags, and the Chromium version is pinned and testable — the option that most directly solves the Linux problem, at ~150 MB per platform and a Node runtime inside the trust boundary, *and unverified on Linux WebGPU*. **CEF** is the same story with a heavier build. **Tauri** has the best licence and the obvious fit for a Rust backend but is not viable for a WebGPU UI on Linux. **A hybrid is worth serious consideration**: a thin Tauri/Wry shell for platform integration — file associations, pickers, tray, single-instance — with the image canvas on a **native wgpu surface** rather than WebGPU-in-webview. That keeps wgpu/Vulkan and reuses the same WGSL, at the cost of a split rendering architecture and a rewrite of how client stages reach the screen. A community workaround doing exactly this (native wgpu composited with the webview) is reported working on Windows 11 ([tauri discussion #11944](https://github.com/orgs/tauri-apps/discussions/11944)).

### The catalogue — the largest single risk in the port

**Immich *was* the asset manager.** Decoupled from it, Sidecar risks becoming a developer without a library, which is precisely darktable's standing criticism: weaker file management, "creating, renaming, and moving files in Darktable is not possible", and no cataloguing-at-import ([Skylum](https://skylum.com/blog/darktable-vs-lightroom); [Imagen](https://imagen-ai.com/valuable-tips/lightroom-vs-darktable/)). The lowest-risk model is the one darktable uses and that Sidecar's XMP design already matches: **the database is a rebuildable cache, the sidecar is the truth.** darktable's XMP holds the full history stack, tags and ratings, so sidecars can rebuild the database, and re-importing refreshes a database entry from its XMP ([pixls.us](https://discuss.pixls.us/t/reload-sidecar-files/35339)). digiKam's shape is informative too: SQLite by default, split into four files — `digikam4.db` (core, "the most important file" for backups), `thumbnails-digikam.db`, `similarity.db` for fuzzy/duplicate search, `recognition.db` for faces — which suggests face recognition and perceptual-hash duplicates are bolt-on subsystems rather than core schema ([digiKam docs](https://docs.digikam.org/en/setup_application/database_settings.html)).

Table stakes for a first release: add a folder as a watched collection with recursive scan; a thumbnail/preview cache keyed by content hash and mtime; star rating, pick/reject flag, colour label; keywords; filter and sort; and write everything to XMP. A **catalogue-free "just browse a folder" path is a real expectation, not a niche one** — darktable users ask for it explicitly ([pixls.us](https://discuss.pixls.us/t/can-i-use-dark-table-without-importing-catalogue-just-with-file-browser-and-side-car/17407)). darktable's reported failure modes are a direct warning list for Sidecar's sync logic: importing a folder that already had sidecars **overwrote them with blank files**; edits were lost migrating macOS→Linux by copying `library.db`; and the startup XMP check prompts on sidecars seconds newer than the database ([pixls.us](https://discuss.pixls.us/t/lost-edits-in-darktable/34548)). So: never write an XMP during a scan, compare content rather than only mtime, and offer one explicit conflict resolution rather than a per-file modal. Identify images by stable content identity (hash of the raw payload, or body serial + shutter count + capture time) rather than path, and re-link on rescan — though **no primary source documents how any of these tools actually matches a moved file**, so this is reasoned design, not established practice. Lightroom's and Capture One's catalogue structures could not be sourced; treat the common claim that `.lrcat` is SQLite as unverified.

### Culling — where the port is an advantage, not a cost

The decisive mechanism is reading the camera's **embedded JPEG preview** instead of rendering the raw. One reported test on 1,000 raw files: **27 min 35 s with standard previews versus 3 min 07 s with "Embedded & Sidecar"**, with culling able to begin while the rest still imports ([HaveCameraWillTravel](https://havecamerawilltravel.com/workflow/lightroom-classic-new-embedded-previews/)). This is **a single test from a workflow blog and should be cited as indicative only** — no vendor benchmark or controlled study was found, and no sourced figures exist for expected slider-to-pixel latency, VRAM footprints or minimum hardware. The known cost is fidelity: "JPEG images do not contain enough information to be able to judge underexposure and overexposure" ([PhotographyLife](https://photographylife.com/how-to-cull-your-images-faster-with-fastrawviewer)), which is why **a raw-derived highlight/shadow warning computed from the raw histogram — cheap, no demosaic needed — is the differentiating feature**, and squarely within what Sidecar's WGSL pipeline already does. A browser+server editor is structurally disadvantaged here because every preview crosses an HTTP boundary; a desktop build can memory-map the raw and hand the embedded JPEG straight to the GPU. Requirements: embedded JPEG in the first frame, asynchronous upgrade to a full render, keyboard-only rating with no round trip, and a background preview queue that is interruptible and prioritised by what the user is looking at. Lightroom's idle-time replacement of embedded previews with standard ones is itself a complaint ([Acciopix](https://acciopix.com/blog/culling-in-lightroom)) — background work must never degrade an already-fast path.

Sidecar is already partway into the pro-judgement toolkit: focus peaking and an AF-point overlay are culling tools even Lightroom lacks in that form. What is missing is the surrounding workflow — ratings, labels, flags, compare/survey views, filters, collections. And the culling-AI race is being fought right now, all of it new or beta: Capture One's **Assisted Review is still in beta** and can run automatically during tethered shooting but is desktop-only ([dpreview](https://www.dpreview.com/news/capture-ones-latest-update-includes-automatic-culling-and-more-canon-support/)); ON1's Culling Assistant is MAX-tier; Lightroom v15.4 (June 2026) added automatic duplicate detection into review stacks. **Sidecar runs ML locally, which is the differentiating axis against Adobe's cloud approach** — a place to be contemporary rather than catching up.

### Colour management, per platform

Linux changed fundamentally: `color-management-v1` shipped in **wayland-protocols 1.41, February 2025**, is at staging version 3, and carries colour properties as immutable **image description** objects ([Phoronix](https://www.phoronix.com/news/Wayland-Protocols-1.41); [wayland.app](https://wayland.app/protocols/color-management-v1)). The natural design is to **not try to read the monitor profile out of the OS at all**: fetch the output's or surface's image description, call `get_information` for either the parametric form or an ICC file descriptor, render to that, and set a per-surface rendering intent. Perceptual is mandatory; optional intents include relative-with-black-point-compensation and **absolute without adaptation, which the protocol itself annotates as useful for proofing**. ICC constraints the client must respect: version 2 or 4 only, three-channel only, Display or ColorSpace class only, 32 MB maximum — and a non-conforming profile produces a *failed* image description rather than a protocol error. Creation is asynchronous, so only a `ready` object may be used. Multi-monitor falls out structurally: the preferred description is per surface with change notifications, so moving a window between differently-profiled monitors arrives as an event and the app rebuilds its output transform and LUT. The deliberate limits matter: **no way to measure or calibrate displays, and the client cannot set an output's profile.** A retrospective says the work "focuses almost entirely on the entertainment side of things, like watching video or playing games" and that professional colour management is still missing "mainly because display measurement is not yet supported" ([OSNews](https://www.osnews.com/story/141803/12-years-of-incubating-wayland-color-management/)). Toolkit adoption through 2025: SDL (Feb 2025), wlroots, Qt 6.10/6.11 (Nov 2025), Chromium enabled by default, GNOME Mutter ICC support merged around August 2025. The Arch Wiki notes the **user interface for managing these profiles is not properly implemented** and documents manual `colormgr device-add-profile` steps ([ArchWiki](https://wiki.archlinux.org/title/ICC_profiles)).

Windows is the awkward platform. `AdvancedColorInfo` is **UWP-only** — "desktop apps (which don't have a CoreWindow) can't use it" — forcing the Win32/DXGI route, and the state can change at any time by user action or OS policy ([Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.display.advancedcolorinfo)). Worse for any "just use lcms2 against the display profile" design: Microsoft says Advanced-Color-aware apps **"should transition away from directly interacting with display ICC profiles"**, and that when Advanced Color is active on either SDR or HDR displays, display-ICC-profile behaviour changes **in non-backwards-compatible ways** ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/wcs/advanced-color-icc-profiles)). Hardware calibration routes through a privileged MHC2-tagged ICC profile that overrides other sources ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/wcs/display-calibration-mhc)). **macOS ColorSync specifics were not reached and are unverified in this research**, as is **macOS EDR entirely** — no source on `CAMetalLayer` EDR properties or how a wgpu/MoltenVK app reaches the EDR path, a real gap for the "macOS plausible" part of the plan.

Library choice is comfortable. Verified or well-supported permissive: **lcms2 MIT** (checked on the GitHub repo sidebar; the `COPYING` path 404'd, so **read the actual LICENSE file in a clone before vendoring**), **OpenColorIO BSD-3-Clause** (LICENSE file fetched), **moxcms Apache-2.0 OR BSD-3-Clause** (pure Rust, "Simple Color Management in Rust", 0.8.1; checked via [licenses.dev](https://licenses.dev/cargo/moxcms/0.8.1) and cross-checked on [depscope](https://depscope.dev/pkg/cargo/moxcms), **upstream LICENSE files not read**), **qcms MIT** (standalone Rust, not an LCMS wrapper), and the **lcms2 / lcms2-sys Rust bindings MIT** (lcms2-sys vendors LCMS 2.19.1). moxcms is the most interesting for Sidecar — pure Rust, no C dependency — with maturity as the obvious risk (pre-1.0, single maintainer); qcms is Firefox-hardened but deliberately lightweight and not built for proofing with intents and BPC. The right shape either way: **parse ICC and bake transforms into 3D LUTs on the CPU at profile-change time; sample them in WGSL. Neither library needs to be in the per-frame path.**

### HDR output

Gain maps won. **ISO 21496-1 was published in July 2025**, jointly developed by Adobe, Apple and others, and both Apple's Adaptive HDR and Google's Ultra HDR build on it; **Android 15 writes both Ultra HDR v1 XMP and ISO 21496-1 metadata by default**, with the ISO metadata in APP2 and the XMP in APP1 so a file can carry both and legacy readers still work ([Android Authority](https://www.androidauthority.com/google-apple-hdr-photo-standard-3495035/); [ultrahdr-rs docs](https://lib.rs/crates/ultrahdr-rs)). Apple added read/write APIs in macOS 15 / iOS 18. Display support is good on Apple (Safari gained extensive HDR in the v26 updates; on iPhone/iPad all browsers have HDR because they are WebKit) and on Chrome/Android, while **Firefox is the consistent hole on macOS, Windows and Android**; Chrome desktop needs a dev flag for AVIF *gain maps* specifically; and **JPEG XL supports gain maps in the format but no browser decodes them** ([Greg Benz](https://gregbenzphotography.com/hdr-display-photo-software/); [Jake Archibald](https://jakearchibald.com/2026/jpeg-xl-vs-avif/)). So the ranking is clear: **gain-map JPEG first** (displayed as HDR across Apple, Android and Chrome; degrades to a correct SDR JPEG everywhere; encoder libultrahdr is Apache-2.0 per the Arch package, the cleanest licence in the set), AVIF with PQ/HLG second (libavif/rav1e/dav1d all permissive, but gain maps are flag-gated in Chrome), JPEG XL third. **Write both metadata blocks rather than choosing**, as Android does. Android's **2.3-stop headroom cap** is worth surfacing in the UI.

Two conflicts to record rather than resolve. **JPEG XL browser status is contradictory across sources** and should not be stated confidently: one says Chrome 155 began decoding on 6 October 2026, others say Chrome 145 shipped it behind `chrome://flags/#enable-jxl-image-format`, and a vendor blog claims universal native support across all major browsers, which the flag-gated accounts contradict; for Firefox, one source says 158 on by default (13 Oct 2026), another says still in progress, another says v152 behind a flag. Safari has decoded JPEG XL since 17.0. libjxl itself is licence-clean — **BSD-3-Clause with an additional patent grant**, Google's `PATENTS` file granting a royalty-free licence covering the implementation — with the minor residual that the PATENTS file names only Google though Cloudinary was also a main contributor ([libjxl PATENTS](https://fossies.org/linux/libjxl/PATENTS)). Second, and more consequential: **the browser HDR canvas route is Chrome-led and partly proposal.** Chrome 129 introduced HDR on the WebGPU canvas via an "extended" tone-mapping mode with `rgba16float` ([Chrome 129 notes](https://developer.chrome.com/blog/new-in-webgpu-129)), and WebGPU already accepts the `rec2100-*` predefined spaces because it reuses the same enum ([GPU Web minutes](https://github.com/gpuweb/gpuweb/wiki/GPU-Web-2023-06-28)), but Chromium's own explainer ties HLG and PQ to `rgb10a2unorm` formats "should they become available" ([webgpu-hdr EXPLAINER](https://github.com/ccameron-chromium/webgpu-hdr/blob/main/EXPLAINER.md)). **Native wgpu/Vulkan is the right path, and ROADMAP's framing of HDR display as gated on a Safari HDR canvas should be rewritten around the native target instead.** One internal representation serves all three platforms: scRGB-style linear float plus BT.2100 — which is both what WebGPU's `rgba16float` + `rec2100-display-linear` describes and what the Wayland protocol's predefined `windows_scrgb` / `windows_bt2100` descriptions hint at. Rec.2020 SDR export remains small and well-bounded: the matrix is standard and a Rec.2020 ICC profile can be synthesised from primaries plus transfer function with lcms2 or moxcms rather than shipping a third-party profile binary.

### Metadata, formats and patents

**Metadata is the sharpest licensing trap in the port.** The complete stack is GPL top to bottom: rexiv2 wraps gexiv2 which wraps Exiv2, and because it links those "too is made available under the terms of the GPL", listed GPL-3.0-or-later on crates.io; `gexiv2-sys` carries the same ([rexiv2](https://github.com/felixc/rexiv2)). ExifTool is Perl. The permissive composition is: **little_exif** (Apache-2.0 OR MIT, pure Rust, the only pure-Rust crate with true EXIF read *and write* across PNG, JPEG, HEIF/HEIC/AVIF, JXL, TIFF, WebP) for EXIF; **Adobe's XMP Toolkit SDK** (BSD-3-Clause, XMPCore + XMPFiles) or a verified-permissive pure-Rust XMP crate for the sidecar; **lcms2** (MIT) for ICC ([little_exif](https://github.com/TechnikTobi/little_exif); [adobe/XMP-Toolkit-SDK](https://github.com/adobe/XMP-Toolkit-SDK)). IPTC is the weak spot — IPTC-IIM legacy blocks and IPTC Core (which is XMP) need the toolkit or hand-rolled parsing. **Maker notes are the real completeness gap**: ExifTool's value is its per-camera tables and no permissive library matches them, so keep ExifTool as an *optional external binary the user installs*, never linked — the same boundary already accepted for libheif. Note that writing XMP for Sidecar's own history needs no heavyweight library at all; the library is only for interoperable namespaces and for round-tripping what other tools wrote. Must-check before any enters a dependency list: **xmpkit, xmp-writer, xmp_toolkit and exiftool-rs licences were not confirmed**, and little_exif's completeness versus ExifTool — tag coverage, maker notes, and whether it writes into raw containers like CR3/NEF/ARW rather than only TIFF/JPEG — was not evaluated.

On formats, decoding is mostly fine permissively. Raw decode is effectively "port from LibRaw (CDDL-1.0, permitted with a header-preserving port) or implement from specifications and papers" — rawler, rawloader, darktable and RawTherapee are all excluded. The one live patent exposure is **HEVC**. Access Advance "manages and administers the HEVC Advance Patent Pool for licensing over 29,000 patents essential to HEVC/H.265" and its FAQ says you "most likely need a license if you sell any products that have HEVC/H.265 encoding and/or decoding capability", with royalties stated for "HEVC Software sold separately from a device"; 28 companies executed licences in H1 2026 ([Access Advance](https://accessadvance.com/topic-what-do-we-license/); [FAQ](https://accessadvance.com/faq/)). The carve-out a free desktop app would rely on — that application-layer software downloaded after the device sale and running on a general-purpose CPU is exempt — is **a 2016 statement that does not appear in Access Advance's current description of what it licenses** ([Beamr, 2016](https://blog.beamr.com/2016/11/30/patent-pool-hevc-advance-responds-announces-royalty-free-hevc-software/)). **Treat that as unresolved legal risk, not a cleared path.** The existing decision to shell out to an external HEIC decoder is doubly justified — it avoids LGPL linking *and* keeps HEVC decoding functionality out of the published artefact — and should extend to HEIC *encoding*, i.e. don't ship it. AVIF is the deliberately royalty-free alternative, but **AOMedia's and Sisvel's AV1 patent posture and the licences of dav1d/rav1e/libavif were not verified** and need their own check; so was the **Adobe DNG SDK licence and DNG patent terms**.

### Packaging, signing and local-server safety

Linux is effectively free: Flathub as the primary channel plus an AppImage for distro-agnostic installs, and let distro maintainers do .deb/.rpm — though **Flathub's own documentation was not fetched and the "free, builds on Flathub infrastructure" claim is inference**. Flatpak interacts with Sidecar's design specifically: a sandbox needs explicit filesystem permissions for photo folders (portal-based access or a broad `--filesystem=home`) and Vulkan/Mesa runtime extensions for GPU access. Both routine, both to be designed for rather than discovered late.

macOS and Windows both have a **money-and-identity gate**. macOS: the paid Developer Program is about $99/year (waivers exist for nonprofits, schools and government, generally not for individuals), and notarisation needs a Developer ID certificate, hardened runtime, secure timestamp, no `get-task-allow`, then stapling — and a signed-but-un-notarised app is still blocked by Gatekeeper. One 2026 source reports Homebrew has **disabled casks for apps failing Gatekeeper checks since 2026-09-01**, which would close the most natural macOS channel; **this rests on a single secondary source and should be confirmed against Homebrew's docs before it drives a decision** ([flaviocopes](https://flaviocopes.com/apple-developer-free-vs-paid/)). Windows is structurally hardest, and the ~$120/year is the minor part. Azure Trusted Signing (renamed "Artifact Signing") is about $9.99/month for 5,000 signatures; eligibility is the problem. Microsoft documents availability "to organizations in the USA, Canada, the European Union, and the United Kingdom"; one source adds a requirement for a **verifiable organisational history of three years or more** and says individuals are limited to the USA and Canada; another gives a list of 12 countries. **The sources disagree on the country list, and no open-source-specific pricing or eligibility was found** ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [textslashplain](https://textslashplain.com/2025/03/12/authenticode-in-2025-azure-trusted-signing/)). A project without a three-year-old legal entity in an eligible country cannot use the service, and unsigned Windows binaries mean SmartScreen warnings on every download.

With Immich gone there is no user database, no sessions and no tokens. For a single-user desktop app the right answer is **no authentication plus strict isolation**: bind only to `127.0.0.1`, take an OS-chosen ephemeral port and tell the client what it is, and require a per-launch random token on every endpoint. **This entire threat model is unsourced inference in the research**, but the risk classes are standard: any page the user visits can send cross-origin requests to `http://127.0.0.1:<port>` (reject foreign `Origin`/`Sec-Fetch-Site`, force preflight with a non-simple header or the token, never use cookies for auth); DNS rebinding (validate the `Host` header against an allowlist); port squatting (ephemeral port plus token, fail closed on a bind failure rather than falling back); and local multi-user machines, where a **unix-domain socket with filesystem permissions removes the whole browser-origin attack class** — but is not reachable from a browser, so it only works behind a shell that can proxy. Another point in favour of a native shell. Path traversal becomes much more serious once the server reads arbitrary user folders rather than Immich-supplied paths: canonicalise every client path and check it against configured collection roots. The port also inherits data-ownership duties Immich carried: atomic XMP writes (write-temp-then-rename), never writing to a folder the user has not added, and a visible, deletable cache under XDG/Library/AppData conventions.

### Performance

The two complaint themes that recur across every one of the six products are **interaction/organisation quality and responsiveness** — which are the real table stakes behind the feature lists. Sidecar's GPU-first design is a genuine advantage on the second: "the DeepPRIME options are demanding" and one review says you cannot see their effect in real time on many systems ([amateurphotographer](https://amateurphotographer.com/review/dxo-photolab-9-review/)), which is exactly the failure mode Sidecar avoids. ON1's 2027 cycle headlining "Faster and More Stable Performance" is a vendor conceding the prior version's performance. **VRAM is the constraint a wgpu editor hits first**: a 60 MP raw at 16-bit RGBA is roughly 480 MB as a single texture, so a tiled or mip-limited pipeline with an explicit VRAM budget and graceful degradation to a lower-resolution working copy when zoomed out is necessary rather than optional. WebGPU may also run on a software-emulated GPU, so detect and warn about software rendering rather than silently crawling ([Chrome troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)). Sidecar's worker/API split is an asset: the queue exists; what is new is that it must be driven by UI attention rather than server-side job submission.

### Explicitly out of scope, and say so

**Tethering.** libgphoto2 is the only realistic cross-platform library and it is **LGPL — excluded even dynamically linked** (SourceForge says LGPLv3, an older Debian copyright records LGPL-2.0+; either way excluded, so the ambiguity does not change the conclusion) ([Wikipedia: gPhoto](https://en.wikipedia.org/wiki/GPhoto)). Compliant routes in order of effort: invoke the `gphoto2` CLI as a separate user-installed process (the Entangle GPLv3+ frontend over an LGPL library shows the boundary is real and respected); implement PTP-over-USB directly on a permissive Rust USB stack — **but `rusb` wraps libusb which is itself LGPL-2.1, and `nusb` as a pure-Rust alternative was not verified; a pure-Rust USB stack is a prerequisite and a material unresolved item**; or vendor SDKs, which are proprietary and redistribution-restricted. It is where Capture One spends its differentiation budget — wireless with proxy-raw-first transfer — and an Apache-2.0 project cannot match per-body coverage. Live view and most exposure control are vendor-specific extensions on top of PTP, which is exactly why libgphoto2's driver tables are valuable and hard to replace. Studio feature, not v1.

**Display profiling.** See finding 3. Consume profiles; never measure.

**Printing.** The research is honest that this is **unresearched, not deprioritised**: no primary material was found on print-module layout expectations, output sharpening by paper type and ppi, the 16-bit print path per OS, or any 2026 data on how much photographers print; the complaint threads found are 2018–2020. The one durable point is that **double colour management — app applies the printer profile and the driver applies it again — is the recurring mechanism behind "the print doesn't match the proof"**, which makes application-managed colour a first-class UI concern rather than a buried setting ([Adobe forum](https://community.adobe.com/t5/lightroom-classic-discussions/printing-issues/m-p/9841392/highlight/true)). The judgement — and it is flagged in the notes as a judgement, not a finding — is that the high-value low-cost subset is **soft proofing plus a correct 16-bit TIFF export with an embedded output profile**, letting the photographer print through whatever they already use. RawTherapee's README states it "is not aiming to offer Digital Asset Management, printing, or uploading" — a mature project declining this axis entirely.

## What not to build

darktable's deprecation list is the most useful single artifact in this research: **a GPL project publicly declaring which thirteen tool concepts turned out to be dead ends** — basic adjustments, channel mixer, contrast brightness saturation, crop and rotate, defringe, fill light, global tonemap, invert, levels, spot removal, tone mapping, vibrance, zone system ([darktable modules](https://docs.darktable.org/usermanual/stable/en/module-reference/processing-modules/)). Do not build `global tonemap`, `fill light`, `levels`, `contrast brightness saturation`, `zone system` or a legacy `channel mixer`; the replacements are a scene-referred display transform, a tone-equalizer-style zonal control, `color balance rgb`-style grading and proper colour calibration. Read the list carefully, though: `defringe` and `spot removal` were superseded by better CA handling and by `retouch`, so their *capabilities* remain wanted.

The honest nice-to-have tail that no RAW photographer will notice missing: liquify, watermarking, time-lapse, sky replacement, double exposure, texture and border packs, posterize, bloom. ON1's own extras — Sky Swap AI, Double Exposure, Split Field, Motion, Textures, Borders, AI Style Advisor, Colorization — are the shape of that tail ([ON1 press release](https://www.on1.com/press/on1-announces-photo-raw-2026-with-advanced-ai-tools-masking-layers-and-new-creative-filters/)). Beyond a single heal/clone, **frequency separation, liquify, layer compositing and content-aware/generative fill are not table stakes for a RAW developer**: the counter-evidence is that darktable and RawTherapee, the two tools with the deepest processing, have essentially none of them and are not criticised for it — the criticism they get is about asset management. Also skip: BM3D in WGSL (block matching plus a 3D collaborative transform with scatter-add aggregation and genuine divergence — "possible but a project, not a feature"; non-local means with a VST gets most of the way with none of the pain); the domain transform, whose recursive 1D sweeps are the worst GPU fit in the survey and whose authors' own FAQ warns that for denoising "the main issue with noisy images is finding robust estimates for their derivatives, which cannot be done using simple forward differences" ([project page](https://www.inf.ufrgs.br/~eslgastal/DomainTransform/)); moving the editing controls from OKLCh to Jzazbz, where the marginal gain is modest and Jzazbz's PQ-like nonlinearity costs transcendentals per pixel — and where a practitioner's caution applies that **perfectly hue-preserving compression is probably not achievable at all**, since holding hue constant in a perceptual approximation does not hold perceived hue constant ([pixls.us](https://discuss.pixls.us/t/module-proposal-gamut-compression/52532?page=4)); and a 2024 chroma-compression method that notes its own computational cost "is high, which limits deployment" ([arXiv 2409.16032](https://arxiv.org/pdf/2409.16032)). Finally, note that darktable crossing into AI in June 2026 — an optional AI subsystem behind a CMake flag, an AI object mask in the mask manager, and a neural restore module covering raw denoise, denoise and upscale — **removes "open source has no AI" as a Sidecar differentiator**; ML masks are now matched in kind, though not in breadth.

## Conclusion

The research reframes the port: the risky work is not the shaders, it is the three things Immich and the browser were quietly doing. The shell question is genuinely unresolved and determines whether Sidecar can be colour-accurate at all — a browser cannot tell the page the monitor profile, so a browser-only build is inaccurate on wide-gamut and HDR displays by construction, independent of the WebGPU problem. That argues for a native shell on grounds that have nothing to do with Tauri's WebGPU stance, and it means the honest sequencing is **shell and catalogue first, features second**, with the multi-frame memory model decided during the port rather than retrofitted after.

The licensing pattern is the other thing that generalises. Four of the five blockers are licence findings, and three of them are *weights or datasets* rather than code: SegFormer's non-commercial weights, Real-ESRGAN's absent weights licence, LaMa's mirror-asserted Apache-2.0 over unverifiable Places2 terms. A weights file with no licence statement grants nothing, and is in practice worse than a stated non-commercial licence because there is no permission to point at. The useful inversion is that **raw denoise is the one large ML feature where this solves itself** — the project has to train on its own camera noise profiles anyway, so MIT noise-synthesis code over an Apache-2.0 architecture produces weights Sidecar owns. That makes denoise simultaneously the most-wanted ML feature by revealed preference (DxO built a product line on it alone; Adobe put it in the Detail panel) and the cleanest one to ship. Everything else learned should be fetched on demand with its licence shown, trained in-house, or left out.

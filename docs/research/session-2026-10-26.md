## How it was worked, and what that means for the results

- **Not in the dev container.** `./dev/run` wasn't available in the session's environment, so everything was built
  and tested on the host: Rust through `cargo` with LibRaw's system dependencies installed, the GPU passes on Mesa's
  llvmpipe (Vulkan, CPU), the browser on Chromium's SwiftShader WebGPU, Emscripten 6.0.13 from a local emsdk. The
  numbers below come from there. Headless Chromium can't present a WebGPU canvas, so nothing on screen was judged
  by eye; the photo is read back through test hooks (`?inspect`) instead.
- **Real files**, from rawpy's test set (Canon CR2s, one truncated, one sRAW) and NASA's ISS photographs (Nikon
  NEFs), under `testdata/cache/samples/`, plus one iPhone 17 Pro ProRAW the owner supplied, under
  `testdata/cache/proraw/`. None of them is committed.
- **A scratch Sidecar** (`sidecar dev` on 127.0.0.1:8089 with an editing folder in the scratchpad) stood in for a
  server. The real deployment on 8090 was never touched, nor were the libraries under `/mnt/storage` or the
  Immich containers.
- **CI** ran green on every push to #44: `rust`, `parity`, `ml`.

## 1. The decode pipeline, reviewed (#42)

*Asked:* review how an image is developed — where decoding can go wrong, why the highlights took so many pull
requests, what the industry does, readability and duplication, optimisations — and start on mobile.

The review is [`pipeline-review-2026-10.md`](pipeline-review-2026-10.md): findings D1–D14 in a table (what, where, the
effect, whether a fix changes pixels, effort), the PR history grouped by theme, industry practice, duplication
worth folding, optimisations, a staged and licence-clean plan for decoding on a phone, and an order of work. Two
later additions on the owner's questions: **a path to reconcile the highlights** (six links in one chain, each with
an owner and a state) and **what the file already says** (fields LibRaw parses that the pipeline estimates
instead).

Two fixes came with it, neither changing a pixel for a file that opened before: **D3**, the shim's mosaic copy
uses `raw_pitch` and refuses a crop wider than the row; **D9**, a camera colour with no calibration resolves with
sRGB primaries instead of panicking. The duplication section was partly folded at once: one colour model for a
developed photo (`SourceSpace` moved into `sidecar-color`), one sRGB curve and half-float conversion in TypeScript,
one list of file types checked against Rust.

## 2. The share target keeps a photo nothing matched (#42)

A photo shared to Sidecar is opened by its checksum, which only finds one the server can already see; anything
else was thrown away. The service worker now keeps it on the phone (`$lib/shared.ts`, Cache Storage, a few and for a
day), and the pick page offers to import it. Found and fixed beside it: **an import into the editing folder kept
its staging name** in its metadata. Found and not fixed: the proxy pre-build races the rename into the folder
(harmless: a wasted decode when it loses).

## 3. The mobile module (#42)

*Asked:* can mobile be decoupled into a module someone adds to their image, the way `-ml` is?

`mobile/` is its own SvelteKit app, served at `/m`, over the main app's `$lib` (one pipeline, not a copy), built
into images with the **`mobile`** and **`ml-mobile`** targets and published as `-mobile` / `-ml-mobile`.

- **Stage 1, a RAW's embedded preview** on the phone at once: JPEG streams are found by their own structure in any
  RAW format, oriented and scaled; checked byte for byte against ExifTool on 13 files.
- **Stage 2, a RAW decoded and developed on the phone:** LibRaw and the server's shim compiled to WebAssembly, the
  ingest shaders run in WebGPU (`web/src/lib/gpu/ingest.ts`, pass for pass as `crates/engine/src/ingest.rs`), and
  one mapping from LibRaw's colour data to a colour model for server and browser (`LibrawColor::camera_color`).
  The phone's proxy matches the server's to half-float rounding (`mobile/scripts/raw-parity.mjs`). Testing it on
  real files found D14.

## 4. The highlight stack, and D14 (#44)

*Asked:* review the whole highlight stack before fixing D14, suspected to be linked.

They were one problem. The pyramid's rescale — ratios against the coarse estimate, averaged under
`exp(c − max(others))` weights — overflowed and turned a truncated CR2 a quarter NaN, and the same step decided the
colour of every reconstructed pixel: measured samples were overwritten, the clipped channels' low ratios were
averaged in, and the weights only made sense in [0, 1]. Measured against ground truth with a new tool,
**`sidecar-dev hilite-truth`** (an unclipped frame clipped on purpose, compared with itself), the old pass was
worse than no reconstruction in the partly clipped band.

`hilite_assemble` and `hilite_doub` are now a bounded fill that keeps what was measured (`hilite_scale` in
`shaders/ingest/common.wgsl`, no `exp`, within 16× the clip level). On three frames at +2 and +4 EV it beats both the
old pass and plain clipping in every bucket; blown cores land 0.05–0.23 stops under the truth instead of
0.15–0.62; the damaged file has no NaN on server or phone; a GPU test on Bayer and X-Trans holds it.
`INGEST_GENERATION` 4. The full write-up with the table is the review's §3, "The highlight stack, end to end".

## 5. Questions answered without code

- **Would 10 or 12 bits help, for the D5's 12-bit lossless NEFs?** Nothing before the screen is 8-bit: LibRaw
  unpacks to 16-bit integers, ingest and develop run in 32-bit float, the proxy is half float (finer than 12 bits
  in the shadows and about 30× below photon noise at the top). Only the canvas (8-bit, dithered) and JPEG export are
  8-bit; 16-bit TIFF export already exists. A 10-bit canvas was built next (§6).
- **Is the D5's Adobe RGB setting taken into account?** It doesn't touch the raw data: the camera's own matrices take
  it to Rec.2020 and then to sRGB or P3, which is what every raw developer does. It matters for camera JPEGs, which
  carry no profile and were read as sRGB — the review's D11, fixed next (§6).
- **Deploying a test build.** HANDOFF's "Deploying a test build", with `--target ml-mobile`; the steps given in the
  session build this branch in a worktree beside the main checkout, keep the old image as `sidecar:previous`, and
  check `/m/libraw/sidecar_libraw.js` is served as JavaScript.

## 6. Adobe RGB, Highlight recovery, a 10-bit canvas (#44)

- **D11.** A camera's Adobe RGB JPEG — `ColorSpace` 0xFFFF with `InteropIndex` R03, or `ColorSpace` 2 — decodes
  with Adobe RGB's primaries and its 563/256 curve (`SourceSpace::AdobeRgb`, `SourceSpace::from_tags`), on the server
  and on the phone (`$lib/local/exif-space.ts`). `INGEST_GENERATION` 5, `META_REVISION` 2.
- **Highlight recovery starts at 0** (the owner's call after §4's measurement): against ground truth the old 0.5
  only added colour error. Stored edits keep their 0.5 with no `PROCESS_VERSION` bump, since every stored edit
  carries the field.
- **A half-float canvas** where the display reports 10 bits or HDR, with the dither cut to a 10-bit step;
  `?canvas=8|16` forces one.

## 7. Apple ProRAW white balance (#44)

*Reported:* on Apple's DNGs Tint has always sat at −150 and Temperature very cold, on photos whose white looks
normal.

The owner's file showed why: ProRAW writes `AsShotNeutral` as 1 1 1 and keeps the white balance in
`AnalogBalance` (2.92 1 1.65), which the DNG specification composes into XYZ → camera as `AnalogBalance ·
CameraCalibration · ColorMatrix`. Neither decode path read it, so the neutral was read in the wrong space: 2,786 K,
tint −158. `camera::dng_xyz_to_camera` composes it on both DNG paths (the review's D2); the shim and the phone's
LibRaw pass the tags through. The same frame now reads **6,880 K +32** in the editor; its as-shot rendering moves by
2.4 / 255. `META_REVISION` 3. An edit that set its own Temperature or Tint on a ProRAW set them on the old, wrong
scale and will render differently.

## 8. The phone runs the one editor (#44)

*Asked:* where the phone can, run the whole app on it: no split before the editor; use the import that isn't
Immich's and load the same editor, which says that some advanced features may be missing because it renders
locally.

The module's small editor is gone. An import made on a phone keeps the original there (`$lib/local/originals.ts`),
and the full editor, finding it, makes the proxy on the device (`$lib/local/develop.ts`) instead of downloading
some 35 MB, and shows "Developed on this device, so some advanced features might be missing", with a link that
develops it on the server instead. Where the device can't — no copy, a linear DNG or sRAW (Apple's JPEG XL ProRAW
among them), too large, no module, any failure — it uses the server's proxy, as before. The local decoders moved to
`web/src/lib/local/`, and LibRaw is loaded at run time from `/m/libraw/`, so the main app builds without
Emscripten. The phone's proxy still matches the server's at 0.06–0.10 % of signal through this way in.

## 9. The interface (#44)

*Asked:* stop the phone zooming the whole interface; have the camera's rendering follow the edit's zoom and
position, controllable from either side; let the loupe go to 150 % and 200 %; and look at the whole interface.

- **No page zoom on a phone:** `touch-action: pan-x pan-y`, Safari's gesture events cancelled, `maximum-scale=1`
  against iOS zooming a focused field (`$lib/page-zoom.ts`).
- **The camera's rendering follows the edit,** crop and straighten included (`placeCamera`), and either pane pans
  and zooms both with the same gestures.
- **The loupe at 100, 150 and 200 %:** a smaller full-resolution tile shown pixel for pixel; double tap or double
  click steps, three buttons pick one.
- **The interface review** is [`ui-review-2026-10.md`](ui-review-2026-10.md): seventeen suggestions, ordered by how
  often someone meets them.

The owner answered nine of them, and those were built (the table at the top of the review): **Mixer** instead of
"Color" (Canadian spelling, and no section named after its group); the phone's Histogram toggle with the photo's
toggles; tools the server can't run **hidden** (`GET /api/capabilities`: Depth without the models, Detail without a
GPU); the phone's panel resized by **press and hold, then drag**, and remembered; a quiet **before/after hint** once
per device instead of a button; **the home page as the phone's way in** (the editing folder by default there, a
RAW's preview while it uploads), with `/m` only sending the installed app to it under a manifest scoped to the whole
app; and on a desktop **one level of folding**, remembered, sRGB / P3 labelled **Output**, and **`?`** for the
shortcuts.
